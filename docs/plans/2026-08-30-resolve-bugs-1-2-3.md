# Resolve Open Bugs #1, #2, #3 - Plan

## Goal Capsule

- **Objective:** Close all three open `bug` issues against the `mantissa` repo (#1 withdrawal_rate silent no-op, #2 wizard demo profile, #3 engine projection horizon = max-of-spouses) with engine-side fixes where possible, not just web workarounds.
- **Authority:** User decision (Path B: full engine surgery for #3) plus the three issue bodies. The web repo has already shipped workarounds; this plan lands the engine fixes so future clients (and the web) can drop the workarounds.
- **Stop condition:** All three issues closed with a comment linking the closing commit. Existing test suite (matrix of 3.9–3.13) green. New tests added where behavior changed. The web repo can drop its `M3.1` workarounds in a follow-up PR.
- **Execution profile:** Three independent units (U1, U2, U3) — small, sequential, one writer. Each unit keeps the existing test suite green and adds targeted coverage for the fix.
- **Tail ownership:** ce-polish runs after all three units land.

## Product Contract

### Summary

Three open `bug`-labeled issues describe misbehaviors that real users (and the mantissa-web wizard) hit:

- **#1 — `withdrawal_rate` is silently ignored under the default `fixed` strategy.** Users who set it see no change, no warning. False-positive "edit didn't take" bugs in clients.
- **#2 — mantissa-web wizard demo profile produces $93B median final NW.** Looks like a broken engine. The web has shipped workarounds; the engine itself doesn't expose "extra capacity" for over-saving plans.
- **#3 — Engine projection horizon = `max(primary.birth + longevity, spouse.birth + longevity) + 1`.** A stub spouse (required for single-household configs) extends the horizon 100+ years, producing lottery-ticket numbers. The web has shipped a workaround; the engine should accept `spouse: null` instead.

### Requirements

- **R1.** When `withdrawal_rate` is set in a config but `withdrawal_strategy` is `fixed` (or unset), `mantissa validate` returns a warning. README documents which strategies use the field. (Closes #1.)
- **R2.** `mantissa schema` and the example `examples/sample_config.json` either omit `withdrawal_rate` from the fixed-strategy narrative, or include a comment explaining the strategy gate. (Closes #1 follow-up.)
- **R3.** `mantissa validate` accepts `spouse: null` (and a missing `spouse` key) without error. The validator distinguishes "no spouse" from "spouse not yet configured" via a warning, not an error.
- **R4.** `Scenario.spouse: Optional[Person]`. Parser permits `spouse: null` and missing `spouse`. All 38 call sites that touch `self.scenario.spouse` guard on `None`. When `spouse is None`, the projection horizon is `primary.birth + primary.longevity + 1`. (Closes #3.)
- **R5.** `withdrawal_rate` field in `Scenario` keeps its current semantic (consulted only by `percent_of_portfolio` and `floor_ceiling`). The fix is documentation + validation, not engine semantics. (Closes #1 without changing behavior.)
- **R6.** Issue #2 is closed by a comment that the web repo shipped workarounds (`web/src/slim/types.ts` stub-spouse, default glidepath, `PlanSummary` interpretation) and that the engine itself doesn't need a "extra capacity" field — the correct behavior is the engine reports terminal net worth, the UI interprets it. (Closes #2 as a documentation/wontfix on the engine side.)
- **R7.** The new `spouse: Optional[Person]` change has parity coverage: a test that runs a single-household plan with no spouse produces the same numbers as a plan with a same-year stub spouse.
- **R8.** No regression in the existing test matrix (3.9–3.13). The CI workflow in `.github/workflows/ci.yml` stays green.

### Acceptance Examples

- **AE1 — Issue #1:** Running `mantissa validate --config <(echo '{"withdrawal_rate": 0.04, "withdrawal_strategy": "fixed", ...}')` prints a warning that the field is unused. The projection still runs.
- **AE2 — Issue #3 (parser):** `mantissa validate --config <(echo '{"primary": {...}, "spouse": null, ...}')` exits 0 with no error about `spouse`. A plan that omits `spouse` entirely also validates.
- **AE3 — Issue #3 (horizon):** Running the projection for a single-household config produces the same year-by-year cash flow as the equivalent two-spouse config where the spouse shares the primary's birth year and longevity. Asserted in a parity test.
- **AE4 — Issue #3 (regression):** Every existing test that constructs a scenario with a real spouse continues to pass. The 38 call sites that touch `scenario.spouse` either use a `Person` directly (no guard) when spouse is required for the code path, or guard on `if scenario.spouse is not None` when the code path is single-household-only.

## Planning Contract

### Key Technical Decisions

- **KTD1 — Issue #1 = validate + docs, not engine change.** Changing engine semantics for `withdrawal_rate` under `fixed` would break every existing config that relies on the current "fixed = base_spending" behavior. Validation + documentation is the minimum-friction fix. The CLI's `mantissa validate` already returns warnings via `ValidationResult.warnings`; the warning is already exposed by the JSON output but not by the human-readable table. Surface it.
- **KTD2 — Issue #2 = close as wontfix on the engine side.** The engine correctly reports terminal net worth for an over-saving plan; the "lottery ticket" feel is a UI interpretation problem, not an engine problem. The web repo already ships `PlanSummary` to handle this. The mantissa issue should be closed pointing at the web fix, with a note that any future "extra capacity" reporting is a separate product decision.
- **KTD3 — Issue #3 = make `Scenario.spouse` `Optional[Person]`, not add a flag.** A `single_household: bool` flag is a band-aid: it would need to be checked at every call site anyway. Making the field Optional and adding `None` guards at the 38 sites is the same number of lines, the same review surface, and the correct type. The trade is that the type changes propagate; the gain is the code accurately represents the domain.
- **KTD4 — Keep `from_config` parser backward compatible.** `spouse: null` and missing `spouse` both work. A real `spouse` object continues to work. The CLI's `mantissa init` template should emit a real stub spouse (matches today's behavior) so existing examples still validate; only new clients can opt into the null form.
- **KTD5 — Engine horizon = `primary.birth + primary.longevity + 1` when `spouse is None`.** No change to the two-spouse horizon. Asserted in a parity test.
- **KTD6 — Don't introduce a new "single" / "joint" enum.** The presence/absence of `spouse` is the only signal. The existing model already has `family_size: int = 2` as a default; we don't need to couple it to spouse.

- Change `Scenario.spouse` type to `Optional[Person]`. Default value: `None`.
- Update `from_config` parser to accept `spouse: null` and missing `spouse`. When `spouse` is null/missing, set `scenario.spouse = None`.

Document the choice in a one-line comment where the call site is non-obvious.

- Add a parser test: `mantissa validate` accepts `spouse: null` and missing `spouse`.
